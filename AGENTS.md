# Workspace storage and build retention (user authorized 2026-11-05)

- Do not accumulate a full Electron/app bundle for each source change. Iterate with
  the independent source host and shared verified original resources; package only
  a reviewable milestone or when packaging behavior is under test.
- All full desktop builds must be direct children of `implementation/desktop/dist`.
  Per platform retain only the current integrity-verified candidate and one pinned
  accepted rollback, as declared in `implementation/desktop/native/build-retention.json`.
  A candidate is NOT evidence of UI/device acceptance. Do not advance rollback based
  on version order, compile success or file hashes alone; record actual acceptance.
- `build-payload.py` automatically verifies a new full build, promotes the candidate,
  and invokes `retain-builds.py --apply`. A failed build never replaces the retained
  candidate or rollback. Cleanup failure must be reported and resolved in the same task.
- Before deleting a superseded generated package, archive its independent payload
  sources/build metadata, verify archive hashes, and retain its manifests, receipt,
  screenshots and test reports. Reuse original artifacts and stock runtime caches.
  Never delete `packages`, `recovered`, Git history, profiles or another product to
  make room without a separately scoped user request.
- Cleanup skips packages used by running processes or carrying `.build-in-progress`, and rejects unsafe paths or
  source hash mismatches. Do not bypass these checks; stop the owned test process
  or investigate the mismatch, then rerun cleanup.
- Payload-only intermediates and failed partial builds are temporary: remove them
  within the task after preserving relevant diagnostics/source, never treat them as
  a new rollback. Keep this distinct from deleting original research evidence.
- At task completion confirm `python3 implementation/desktop/native/retain-builds.py`
  reports no stale packages, and report disk usage after substantial cleanup.
  Do not generate extra full bundles merely to test the retention mechanism.

## Source-first restoration for all user-reported issues (2026-11-05)

- Treat this as the default workflow for every current and future issue in this workspace, not only composer alignment. Required order: check official public source → trace the version-bound artifact implementation → identify the missing host integration → restore the original mechanism → validate the reported interaction. Do not start with a replacement implementation and investigate the source afterward.
- This applies to EVERY user-reported problem, including layout, interaction, state, navigation, lifecycle, message flow and Remote. First trace the original implementation in official source and version-bound shipped artifacts. Check whether public `https://github.com/openai/codex` already supplies the implementation, contract or tests before repeating reverse engineering. Bind upstream evidence to a commit and distinguish it from the frozen artifact version.
- Prefer restoring original components, configuration, initialization, state ownership and call paths. Determine whether the independent host omitted an original mechanism before changing behavior. Do not jump directly to custom CSS, DOM repair, replacement components, arbitrary state/key changes or protocol substitutes merely because they make the symptom disappear.
- Before a production-path fix, record the original file/symbol, expected mechanism, missing or incorrect integration, and runtime evidence. A visually successful workaround is not evidence of faithful restoration.
- If original evidence is insufficient, record the precise gap and continue targeted investigation. Keep exploratory independent patches isolated and explicitly labeled; do not silently promote them as recovered official behavior. Never overwrite original packages or recovered evidence.
- Public Codex source availability does not prove that the desktop renderer, ChatGPT Web, mobile UI or cloud service implementation is included or version-compatible. Inspect the repository before asserting scope or reuse.
- Each fix report must identify the source evidence, restored mechanism, independent adaptations (if any), and validation result. A newer upstream/artifact mechanism ported into the frozen baseline must be labeled a compatibility adaptation, not same-version source recovery. If no source-backed repair is established, report the unresolved boundary rather than declaring a speculative workaround complete.
